0. DECISIONS LOCKED IN (from the grill session — do not relitigate these)
===============================================================================

- Currency:        EUR-only. Strip all per-account currency / FX plumbing.
- Architecture:     Vite + Preact + TypeScript. Build step is fine (Vercel).
- Quick entry:      Center FAB -> keypad-first bottom sheet with smart recall
                    chips (recency + frequency ranked), 3-tap happy path.
- Dashboard shape:  Hero number (this month vs usual + net worth) + ranked
                    insight feed below it + account strip. No more than
                    ~1.5 screens before you're into "tap for detail".
- Visual direction: Dark fintech. Dark-ONLY (no light mode, no toggle).
                    System fonts, tabular figures for amounts, bold numbers,
                    accent gradients, 44px min touch targets.
- Category types:   Keep all 6 (income, expense, transfer, non_income,
                    non_expense, receivable, payable) but relabel in UI:
                      non_income -> "Money back"
                      non_expense -> "Paying someone back"
                      receivable -> "Lent out"
                      payable    -> "I owe"
- Merchants:        Rename subcategory -> merchant. Free-text + autocomplete.
                    One-time guided merge screen for duplicates
                    (EDEKA/Edeka/KAUFLAND HAMBURG BRAMF etc) — user approves
                    every merge, nothing auto-merged silently.
- Sync:             Fix Google Drive sync properly: token refresh via GIS,
                    debounce uploads (~5s), revision/ETag conflict detection,
                    honest status UI (Synced/Pending/Offline/Conflict).
                    NOT replaced with a backend. NOT downgraded to manual
                    backup-only.
- Budgets:          None. Insight feed compares against the user's own
                    3/6-month historical average per category. No caps,
                    no nagging.
- PWA:               Full: manifest, icons, service worker, installable,
                    offline-capable app shell.
- Charts:           Drop Chart.js (200KB vendored). Use uPlot (~10-45KB,
                    SVG/canvas tiny chart lib) for the few charts that
                    survive: sparkline, ranked bars, net worth line.
- Navigation:       4 tabs + center FAB: Home | Activity | [+] | Accounts |
                    Settings.
- Rollout:          Hard cutover of the CODE (delete public/* at the end,
                    single new app). But DATA is never overwritten blind —
                    new app reads from new storage keys / new Drive filename,
                    migrating read-only from the old ones. Old data stays
                    intact and recoverable until the user deletes it
                    manually. See Phase 0 and Phase 5.
- Design review gate: Static Home-screen mockups (2-3 variants) must be
                    shown and approved BEFORE any component code is written.
                    This is a hard gate — Phase 3.

CONFIRMED BUGS (file:line references from the current public/ tree, for the
record — these do not need individual fixes since the code is being
replaced, but the new implementation must not reintroduce them):

  B1  Granularity key mismatch: getSourceAccountsSeriesData drops the

  B2  convertAmountToDashboardCurrency is an identity function
      (dashboard.js:322-324) — multi-currency totals are silently wrong
      whenever currencies differ (not triggered today since data is
      100% EUR, but the plumbing exists and is broken).

      computed every keystroke and never read by anything (dead work).
  B4  getTransactionCategoryType's category-type lookup can never

  B5  renderPayablesBalanceChart throws RangeError when `from` is empty
      (dashboard.js:1257-1258) — shiftMonth("") is invalid.
  B6  encodeURIComponent used inside a single-quoted onclick attribute
      without escapeHtml — apostrophes in names break the attribute /
      open an injection vector (dashboard.js:1878-1880, accounts.js:22).
  B7  Missing GOOGLE_CLIENT_ID path never calls loadData() — fresh clone
      without config.js shows a blank app with zero data, no error
      (drive-sync.js:186-193).
  B8  OAuth access token persisted in localStorage with no refresh and
      no expiry tracking — sync dies silently after ~1h
      (drive-sync.js:23-32).
  B9  SYNC_INTERVAL_MS = 1000, full-dataset re-upload on any dirty flag,
      no debounce, no ETag, no conflict detection — last-writer-wins,

      with openingBalance: 0, destroying real opening balances
      (data-utility.js:145-173, db.js:100,104).
  B11 All 4 pages render on every loadData() regardless of which is

    src/
      app/            routing (4 tabs + FAB), shell, safe-area layout
      domain/         types, money (integer cents), dates (UTC-safe),
                      signed-amount (single source of truth)
      storage/        repository layer, v1->v2 migration, localStorage

      sync/           Drive sync v2: token refresh, debounce, conflict

      features/
        home/         hero + insight feed + account strip
        activity/     transaction list, search, filters, detail sheet
        entry/        quick-entry keypad sheet + recall chips
        accounts/     balance cards, sparklines, opening balance edit
        settings/     categories, merchant merge, CSV import/export
      components/     shared UI primitives (buttons, sheets, chips, charts)
      styles/         design tokens (dark fintech palette), globals
    public/           static assets only (icons, manifest) — NOT the app
    dist/             Vite build output
    scripts/          migration-proof script, CSV tools
    docs/             this file + any ADRs

  Money: integer cents (number, safe up to ~9e15 — plenty for personal
  finance), formatted at the edge only. Eliminates float drift class of
  bugs (reduce() sums become exact integer arithmetic).

  Dates: all internal comparisons on UTC-anchored YYYY-MM-DD strings or
  Date.UTC(...) construction. No new Date().toISOString() for "today" —
  use a single getLocalToday() that respects the user's actual timezone
  for "today" boundaries (fixes the Dhaka-at-01:31 bug) while keeping
  storage/comparison lexicographic.

PHASE 11 (Activity screen) — done, with three deliberate deviations from
the phase text above, called out honestly rather than silently:
  - "Virtualized" -> INCREMENTAL RENDER, not true windowing. The list
    renders 80 rows at a time (trackz-app/src/features/activity/
    useIncrementalList.ts), appending another 80 when an
    IntersectionObserver sentinel scrolls into view. Scrolling all the
    way through ~1,500 real rows does eventually mount all of them —
    this is NOT constant-DOM-size virtualization. Hand-rolled
    absolute-position virtualization (measured row heights, a flattened
    index, scroll-offset math) was judged disproportionate to a bounded
    dataset with sticky variable-height month/day headers; revisit as a
    Phase 17 item if a real device shows jank.
  - "Sticky month headers" -> pure CSS `position: sticky`
    (ActivityList.css), not a scroll-position-tracking JS mechanism. The
    browser's native sticky behaviour already produces the "which month
    am I in" handoff correctly as the user scrolls past a boundary, so no
    IntersectionObserver-on-every-header machinery was built.
  - Swipe-to-delete (named in the original Phase 11 scope) -> DEFERRED to
    Phase 17's real-device hardening pass. Hand-rolled touch-gesture code
    (touchstart/move/end tracking, scroll-direction disambiguation) was
    judged the highest-risk, least verifiable-in-session part of the
    original plan — it can only be meaningfully tested on a real iPhone,
    which Phase 17 is explicitly for. The tap-through detail sheet
    (TransactionDetailSheet.tsx) covers every action swipe would have:
    edit (every field via the existing EntryForm, now with an editable
    amount field for the first time — see below) and delete (with a
    same-sheet confirm step and an Undo toast), both reachable via
    keyboard/screen reader for free since rows are plain <button>s.

THE FOUR TRANSPORT BUGS, AS FIXED:
  T1  uploadToDrive never uploaded content. It PATCHed the METADATA URI
      with the SyncDocument as the body; revision/device/transactions are
      not File resource fields, so Drive returned 200 and stored nothing.
      FIXED: content now goes to /upload/drive/v3/files/{id}?uploadType=
      media. drive.test.ts asserts positively (the media URI is used) AND
      negatively (no PATCH to the metadata host exists), because only the
      second assertion fails if someone reintroduces the old call.
  T2  First-ever sync failed by construction. The file was created with
      {name, mimeType, content}; `content` is not a File field either, so
      the file was created EMPTY, and the next fetch called
      response.json() on an empty body -> SyntaxError -> "unknown" -> 5
      retries -> permanent "error". FIXED two ways, deliberately both:
      creation is a single multipart/related upload carrying metadata AND
      content (no window in which the file exists and is empty), and
      fetchFromDrive now reads response.text() and treats empty-or-
      unparseable as "no remote document" rather than throwing. The second
      half is the recovery path for any file ALREADY left empty by the old
      code — without it, an account that ran the broken version could
      never heal.
  T3  ETag conflict detection was impossible, not merely unimplemented.
      Drive v3 lists Files.etag as "n/a" and files.update documents no
      If-Match or precondition, so metadata.etag was always undefined and
      the 412 branch unreachable. REPLACED with convergence on Drive's
      server-side `version` counter: read version, fetch content, merge,
      re-read version, and upload only if it did not move; otherwise
      restart (max 3 rounds, then report "conflict"). ORDERING IS
      LOAD-BEARING and was corrected during implementation: the plan said
      "re-read it immediately before upload", but reading the version
      AFTER the content is actively unsafe — a write landing in between
      leaves us holding stale content stamped with the writer's NEW
      version, the pre-upload check sees no change, and we overwrite them.
      Version is read FIRST; being wrong that way causes only a spurious
      restart. There is a test asserting the call order for exactly this
      reason.
      Version is kept as a STRING and only compared for equality: Drive
      serialises int64 as a string, and "did anyone write?" is an equality
      question, so parsing to Number would add a precision hazard to buy
      an ordering nothing uses.
      This narrows the race, it does not close it. Drive offers no
      compare-and-swap, so that is the best available; the doc comment
      says so rather than implying atomicity.
  T4  Sync was an infinite loop. performSync -> replaceAllTransactions ->
      notify() -> markLocalChanged() unconditionally -> "pending" + fresh
      5s debounce -> performSync, forever: a Drive round trip every five
      seconds for as long as the app was open, and a status indicator that
      could never settle on "Synced". FIXED: replaceAllTransactions takes
      { silent: true }, which still notifies UI subscribers (a transaction
      from another device must appear without a manual refresh) but not
      the sync notifier. Plus the write is skipped entirely when the merge
      changed nothing. The test asserts BOTH directions — no debounce from
      a sync write, and a debounce still armed by a genuine local edit —
      because the obvious over-correction is to silence the notifier
      everywhere.

SECONDARY FINDINGS, ALL ADDRESSED:
  - REACTIVE TOKEN REFRESH now exists. auth.ts claimed refresh happened
    "by the Drive layer if a token is rejected early", but drive.ts never
    called refreshAccessToken(). Only the proactive setTimeout covered
    expiry, and iOS freezes timers in a backgrounded PWA — this app's
    primary target. driveFetch() now refreshes once on a 401 and retries;
    exactly once, because if a token minted seconds ago is also rejected,
    the grant is gone and retrying harder cannot bring it back.
  - accountTypes NOW SYNCS, with per-account updatedAt, merged by the same
    last-writer-wins rule as transactions (tie -> local, matching
    merge.ts deliberately: two different rules for the same question is a
    bug generator). Shape migrated from the old flat map at read time, and
    migrated entries are BACKDATED TO THE EPOCH — stamped "now" they would
    look freshly authoritative and beat genuine recent edits from another
    device. The SyncDocument field is OPTIONAL, and absent must mean "this

THE BUG THIS PHASE FOUND AND FIXED: CSV IMPORT DID NOT REPLACE.
SettingsScreen's handleConfirmImport called replaceAllTransactions(...)

the 5s debounce, and the resulting merge is a UNION BY ID (merge.ts step
2 keeps every id on either side). So every row that was on Drive but
absent from the imported file came back about five seconds later.

  added in commit 1d1e988: re-importing the SAME file, or an export of

  A): the alternative was to express the dropped rows as tombstones so

  THE FAILURE PATH IS REPORTED, NOT SWALLOWED. If the Drive overwrite
  fails (network drops mid-import), local holds the new data, Drive holds
  the old, and — because the local write is silent — NOTHING IS

  ordinary edit arms a debounce, that sync merges against the stale remote
  copy, and the dropped rows return. The original bug, just delayed. So
  the toast names the recovery button ("Replace Drive copy with this
  device") rather than saying "export failed".

SECOND BUG, FOUND BY THE USER RUNNING IT LOCALLY AFTER THE ABOVE: the
Home account strip was scrolling the WHOLE PAGE sideways. The user's own
diagnosis — "margin-auto of activity screen is problematic, it is making
the content shrink" — was exactly right, and was the key: the strip was a
symptom, not the cause, and the same rule was ALSO shrinking Activity.

  ONE ROOT CAUSE, TWO OPPOSITE SYMPTOMS. Measured at a 390px viewport
  before touching anything: Home 480px (overflowing), Accounts 473.8px
  (overflowing), Activity 358.3px (SHRUNK, content visibly pinched),
  Settings 390px (correct by luck — its content happened to be exactly
  viewport-width).
    .app-shell is a COLUMN flex container (added for the removed header,
    kept for the layout). Per the flexbox spec a flex item stretches to
    the cross size only when NEITHER cross-axis margin is auto. All four
    screens carry `margin: 0 auto` to centre the column on a wide screen,
    which DISABLES that stretch — so each screen shrink-to-fit its own
    content, then max-width: 480px clamped whichever ones exceeded it.
    Wide content overflowed the phone; narrow content pinched inward.
    This is why it looked like an account-strip bug: the strip is the
    widest intrinsic content on Home (7 cards x 110px min-width = 850px),
    so it set Home's shrink-to-fit width and dragged the page with it.
  FIX: `width: 100%` on all four screen containers. `align-self: stretch`
  was tried first and measured NOT to work — auto margins beat stretch,
  which is the part of this worth remembering. 100% resolves against
  .app-shell's content box, and globals.css's box-sizing: border-box
  keeps the padding inside it, so each screen is now exactly the viewport
  width up to the 480px cap. Verified 390/320/430: all four screens
  measure exactly min(viewport, 480) with zero horizontal page scroll.
  The strip STILL scrolls internally with all 7 cards present — a fix
  that hid its overflow would have silently truncated accounts, so that
  is asserted separately rather than assumed.
  Mutation-tested: removing `width: 100%` reproduces Home at 480px AND
  Activity at 358.3px, 13 assertions failing; reverted to a zero diff.

  WHY NEITHER THE PHASE 13b NOR THE DEVICE PASS CAUGHT IT. Phase 13b's
  verification asserted "no horizontal overflow at 320px" — of the
  CategoriesSheet it had just built, which was true. The screens behind
  the sheet were already broken and were not measured. The device pass

  component-scoped verification passes while the page is broken, so a
  layout claim needs a PAGE-level assertion (document.scrollWidth <=

  A GENUINE AMBIGUITY, FOUND BY CHECKING AND NOW PINNED: throughout
  JANUARY, this-month and this-year are the SAME range (both 1 Jan ->
  today), so no comparison can distinguish them. Array order decides it and
  this-month wins as the narrower claim, meaning that in January tapping
  "This year" highlights "This month". Cosmetic and inherent to deriving
  rather than storing, so it is documented in matchingPreset's comment and
  asserted by a test rather than left to be rediscovered as a bug.

  MUTATION TESTING CORRECTED THIS PHASE'S OWN COMMENT, for the second time
  in this file (cf. the Phase 15c import fix). The first version of
  matchingPreset's comment said all-time had to be checked FIRST so an
  empty filter would not read as "no preset". Mutation M1 reordered the
  array and ALL 402 TESTS STILL PASSED. Investigated instead of adding a
  test to defend the claim: no other preset can ever produce empty bounds
  (verified across 1 Jan, 9 Jan, 31 Dec and mid-month), so all-time cannot
  be shadowed wherever it sits and the ordering is genuinely redundant
  there. The comment now says plainly that all-time's position is NOT
  load-bearing while this-month-before-this-year IS — the opposite of what
  it first claimed. Same lesson as Phase 6 part 1's dead all-caps tie-break:
  a rule that never fires implies a decision the code does not make.
  Four further mutations, each caught and reverted to a zero diff: swap
  this-month/this-year (1 test, the January tie); compare only the `to`
  bound (4 tests); ignore the passed `today` and default it (4 tests);
